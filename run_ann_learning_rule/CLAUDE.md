# Conventions for `run_ann_learning_rule/`

These rules apply to every `runN/` subdirectory. Each run is an independent replicate of the same mission (see `runN/mission.md`).

The research loop in this directory is driven by the **`research-step`** skill (see `asta-plugins/plugins/asta/skills/research-step/SKILL.md`). It models the research session as a **beads** epic in `.beads/`, with typed sub-issues whose `metadata.research_step.output` matches `assets/schemas.yaml`. **Beads is the source of truth.** `summary.md` is a derived digest, regenerated by the `update-summary` workflow.

## Tool usage

- **Coding/running experiments: use the `run-experiment` (Panda) skill, not ad-hoc Python.**
  Reason: Panda produces standardized experiment artifacts (`experiment.py`, `experiment-trace.txt`, `experiment.html`, `experiment-artifacts.py`) in `.asta/experiment/` that downstream Asta tools consume. Writing the experiment directly skips these artifacts and breaks interoperability even when the numeric results are correct.
  How to apply: every `evidence_gathering` task (and any other research step whose concrete work is "implement + run a training/evaluation script") goes through `run-experiment`. The Panda artifact paths land in `evidence_gathering.output.artifacts[]` and `log_path`. Bypass only for trivial utility scripts (e.g. a one-off plot from existing JSON).

- **Literature reports: render with the `preview` skill after writing.**
  Reason: grep-verifying that `[@key]` entries exist in `.bib` confirms the necessary condition for citations but not that they render. Preview catches formatting, encoding, and citation-processor issues before the report is used downstream.
  How to apply: every time a literature artifact is created or materially updated. The most common case is the long-form notes pointed to by `literature_review.output.summary_path` (typically `background_knowledge.txt`), and any standalone `literature_report*.md` produced as part of a literature review.

- **One-off paper lookups: prefer the `semantic-scholar-lookup` skill over ad-hoc `asta papers get` shell loops.**
  Reason: matches the Asta ecosystem and the skill handles edge cases (missing fields, search ranking) that ad-hoc scripts silently mishandle.
  How to apply: when fetching metadata for ≤ ~10 papers. For bulk cluster searches, `asta literature find` is still correct.

## Project layout

- **`references.bib` lives inside each `runN/`, not in a shared parent.**
  Reason: `mission.md` defines each run as an independent replicate that must keep its evidence separate from sibling runs. A shared parent `references.bib` would mix bibliographies across runs.
  How to apply: any literature report's YAML frontmatter should read `bibliography: references.bib` (same dir), not `../references.bib`.

- **Standard per-run artifacts (aligned with `research-step`):**
  - `mission.md` — research mission (input; written by `brainstorm`, then read-only).
  - `.beads/` — beads database; the source of truth for the research graph.
  - `summary.md` — derived digest, written **only** by `update-summary`. Treat it as read-only for everything else.
  - `background_knowledge.txt` — long-form context for the current step. Typically the `summary_path` target of a `literature_review` task.
  - `references.bib` — BibTeX for all cited work (per-run).
  - Optional step-specific drafts (`literature_report_step<N>.md`, `design_step<N>.md`, etc.) — useful intermediate artifacts; their durable contents must be encoded into the corresponding beads task's `metadata.research_step.output` so the digest and downstream tools see them.

## Research-loop discipline

- **Drive the loop through `research-step` workflows.** Use `brainstorm` for state questions and mission edits, `init` for environment setup, `plan` to grow the graph, `execute` to run a ready task, and `update-summary` to refresh `summary.md`. Hand off between workflows as the skill prescribes.

- **Encode durable results in beads, not in side files.** Every numerical claim, hypothesis, audit verdict, or design decision that future steps will rely on belongs in the appropriate task's `metadata.research_step.output`, matching `assets/schemas.yaml`. Side documents are scratchpads; they are valid during a step but the canonical record is the beads issue.

- **Treat `summary.md` as read-only outside `update-summary`.** When state changes (issue closed, new task added), run `update-summary` to refresh the digest. If you find yourself wanting to hand-edit `summary.md`, that is a signal that an issue's `output` is missing the information instead.

- **Honor the validation gate.** `execute` runs `scripts/validate-output.sh` against the schema before closing an issue. If validation fails, leave the issue `in_progress` and fix the output, rather than closing it with a partial/invalid payload.

- **Follow the research-step skill's prescribed tools.** When a skill says "use X for Y", invoke X. The skill exists to produce artifacts other tools consume.

- **If you deviate, say so up-front before acting.** Describe the deviation and the reason in a user-visible message. State the alternative tool you are using rather than silently substituting one.

- **Negative results are results.** When an experiment falsifies a hypothesis, capture the verdict in the corresponding `analysis.output` (`verdict=refuted`, with `reasoning` and `caveats`), close the issue, and let `update-summary` propagate it. Move on to the next ready task instead of re-tuning the same step in pursuit of a positive outcome.

## Environment

- Python code runs under the `panda` conda environment (`conda activate panda`).
- Detect and use GPU at runtime; fall back to CPU automatically. Log the device at start of each run.
- If a package is missing, `pip install` it within `panda`.

## Independence of runs

- Each `runN/` keeps its reads and references inside its own directory. Sibling runs (e.g. `../run2/`, `../run5/`, `../run6/`, `../run8/`) are out of scope: their `mission.md`, `.beads/`, `summary.md`, `background_knowledge.txt`, `references.bib`, and any other files are off-limits. The goal is an independent trajectory for comparison across runs.
- This convention file (CLAUDE.md) is intentionally the *only* shared context. Everything downstream of it is per-run.
